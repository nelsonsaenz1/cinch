Add clothes — four doors, no favourite
One chooser, four equal ways in, and a guided lead door that appears only while it has something to offer. Thirty-six states of routing, permission timing, consent boundaries and honest conditions — no door is ever disabled by capacity, and no method is styled as a fallback. Implementation handoff
Route & ownershipsrc/app/add-clothes.tsx keeps the route. Every door is drawn from the shared table in src/features/ingest/intake-routes.ts using the existing DoorPlate; the order, labels and descriptions come from that one source so no screen can drift from another. The Ten, capture, /find-photo and /walkthrough are reused as they ship. No new file, package, vendor, permission, data recipient, public surface or billing surface.DEVIATION — three doors vs fourThe directive names three doors: photograph, describe, voice. The shipped contract has four peers, and the fourth is not a duplicate: Find a product photo searches a licensed shop catalogue and returns a licensed product photograph, while Describe by voice files the owner’s own spoken words. Deleting or merging a working route to satisfy an older count would remove a real capability and break the shared table. All four are preserved as equal peers, and the equal-doors law applies to all four rather than to three of them. This is the only departure from the brief.The Ten is not a fifth doorIt is a guided lead door that appears above the peers only while the closet is below its cap, and it disappears entirely at the cap rather than dimming. It is never counted in the peer sentence, never styled as a peer, and never presented as an intake method — it routes into the guided grid that then uses these same methods.Equal-doors lawAll four peers share one size, one plate size, one type scale, one target and one tint weight; only the imagery differs. No door is coloured as primary, positioned as recommended, ordered by likelihood, or marked as a fallback. A door with an active condition keeps its position and its full width — the condition is drawn inside it.Permission timingThis chooser requests nothing. Camera opens capture, where the in-app rationale precedes the iOS request. Photo library uses the system picker, so no broad photo-library permission is ever requested. Voice carries its recording disclosure at its own field in the walkthrough. Nothing on this screen can trigger an OS prompt.Camera conditionsTwo distinct causes, two distinct remedies. Permission blocked: name the cause, offer Settings, keep the other three peers open. Module unavailable in this build: name the build cause and updating as the remedy, and do not offer a Settings control that cannot help. Returning from Settings re-reads the real state and never auto-launches the camera.Processing consentThe gate applies only where a photograph will be processed now — the library door, and the captured photograph at its own boundary. Accept resumes the exact waiting door once, not the last door touched and not twice after a dismissal. Decline is a working on-device mode with manual tagging; nothing uploads afterwards, and the choice is reversible. While the consent state is unresolved no sheet flashes and no door is pre-disabled.Catalogue provenanceProduct search reads a licensed shop catalogue. It is not a web search and no typed text reaches an AI model, so it must never present photo-processing consent. The disclosure travels with the controls rather than living in a legal screen. Spoken catalogue input carries its own recording disclosure at that field.Voice legal line — verbatim"The recording goes to the service that turns speech into text, then to the model that reads the list." It appears above the record action, unshortened and unparaphrased. No fixed vendor is named because the transcription service is a configurable Whisper-class service behind the server; naming one would be false the moment it changes.CapacityCapacity never disables an intake door. Acquisition proceeds and the server settles the real limit after the garment exists, where a truthful remedy can be offered against a real piece. The colophon prints real used and limit for active pieces only, is omitted while the query is unresolved, and is never a bar, percentage, streak or countdown.Deep linksA recognised door parameter runs the identical gates as a tap — same consent check, same resume, same picker. An unknown or invalid parameter falls back to the chooser silently, with no error and nothing written. Cancel at any point writes nothing.PrivacyPrivate photographs and recordings only. No item ID, storage path, signed URL, utterance, transcript, wardrobe content or free text appears in copy, accessibility strings, logs, analytics or error text. The private image fallback is identical for missing, expired and unauthorised images and never reveals which.Analytics allowlistExisting bounded buckets only: intake_door_shown { door }, intake_door_opened { door }, intake_condition { door, cause: permission_blocked | module_unavailable | offline }, consent_result { outcome: accepted | declined }. Forbidden in every payload: item IDs, names or images, exact wardrobe contents, transcripts or utterances, typed search text, price, friend data, raw server error, and free text of any kind.AccessibilityFocus order: title → Cancel → The Ten when present → the peer-count sentence → the four doors in fixed order → catalogue disclosure → capacity colophon → any active condition. Each door is one coherent node reading name then method. The consent sheet traps focus and waits for an explicit answer. Targets are ≥44pt everywhere. At AX-XXXL doors grow and stack with full labels and descriptions, nothing shrinks or ellipsizes, and the list scrolls. At 667pt the title, Cancel and current door stay reachable.MotionDoors settle a few points on entry. Reduce Motion removes the travel and uses a short fade; composition, order, targets and announcements are identical either way.TestsFour doors render in fixed order at identical size and target; no door is styled as primary.
