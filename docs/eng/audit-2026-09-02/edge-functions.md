# Edge Functions Audit — 2026-09-02

Scope: `supabase/functions/*` (Deno, 20 functions + `_shared`) and their callers in `src/` (live App Store app). Audit only — no files under `src/`, `supabase/`, `tests/`, or `scripts/` were modified.

Overall impression: this is an unusually disciplined codebase. Auth model is consistent and well-documented (`supabase/config.toml:406-478` records the reasoning for every `verify_jwt = false` override), quota/throttle claims are atomic RPCs almost everywhere, and most external calls carry explicit timeouts. Findings below are the exceptions to that pattern, not evidence the pattern is absent.

## Top 15 findings (file:line)

1. **Dead function: `packing-brief` has zero callers.** `supabase/functions/packing-brief/index.ts` (355 lines, plus `schema.ts` 130 and `bounds.ts` 256) is fully implemented server-side — auth, consent gate, plan gate, atomic quota claim, retry-with-backoff, the cleanest `{error,message}` shape of any function audited — but is no longer invoked from the client. `src/features/plan/use-packing-brief.ts:9-38,44-61` documents the replacement (an on-device deterministic memo) and says explicitly the Edge Function is "scheduled for removal with the Edge Function itself"; the old `PackingBriefError` class is marked `@deprecated`. No cron, no webhook registration. Confirmed independently twice: orchestrator's `grep -rn "packing-brief" src` and the Group B sub-agent's search both found only comments/doc references, zero `functions.invoke`/`/functions/v1/packing-brief` call sites.

2. **`_shared/pinterest.ts` has no timeout on any external call**, unlike every other integration in this codebase. `tokenRequest()` (`supabase/functions/_shared/pinterest.ts:164`, used by `exchangeCode`/`refreshGrant` — the OAuth token exchange) and `liveGet()` (`supabase/functions/_shared/pinterest.ts:247`, used by `listBoards`/`listPins`) call `fetch()` with no `signal`/`AbortSignal.timeout`/`AbortController` anywhere in the file, and no retry-with-backoff either. Both `pinterest-api` and `pinterest-oauth` inherit this gap. Confirmed independently by the orchestrator and the Group C sub-agent. Contrast with `_shared/openrouter.ts:149-150`, `_shared/push.ts:211,350` (20s timeout + one retry, the codebase's best-covered integration), `sync-feeds/index.ts:200,274`, and `support-mail/mail.ts:119-120,127` — all of which set an explicit deadline.

3. **`delete-account`'s client discards the server's structured failure data.** The server computes `detail` (`'mark_failed'|'delete_failed'`), `failedBucket`, `objectsRemoved`, and `resumable` (`supabase/functions/delete-account/index.ts:219-232,244-255`) to describe exactly what succeeded before a partial failure. `src/features/auth/use-delete-account.ts:22-23` reads only the raw `error` message string (`if (data?.error) throw new Error(data.error)`), and `src/app/privacy/delete.tsx:53-55` just interpolates that message plus a fixed suffix, always offering the same generic "Delete everything again" retry regardless of which bucket failed or how much was already removed. For an irreversible, App-Store-mandated (Guideline 5.1.1(v)) deletion flow, this is the most consequential instance of the server-richer/client-discards pattern found in this audit.

4. **deno.lock version drift across the 4 functions that have one, and no lock file at all for the other 16.** `supabase/functions/garment-search/deno.lock` pins `@supabase/supabase-js@2.112.0`/`jose@6.2.8`; `pinterest-oauth/deno.lock`, `stylist-chat/deno.lock`, and `pinterest-api/deno.lock` pin `@supabase/supabase-js@2.112.3` (the latter two also `jose@6.2.9`). The root `/deno.lock` (RN app) matches `garment-search`'s `2.112.0`, not the other three. `asc-notifications` — verifying Apple's signed JWS payloads, the function's entire trust boundary — imports `npm:jose@^5` (`asc-notifications/index.ts:3`) with no lock file at all, so the exact resolved build isn't reproducible across deploys. Not a correctness bug today (all functions pin only caret ranges in `deno.json`), but a live drift the lock mechanism exists to prevent.

5. **Error-shape inconsistency is systemic: `{error: <slug>}` vs `{error: <human sentence>}` vs `{error, code}` vs 200-with-`ok:false`, with no single convention.** Confirmed across all four groups. `build-export` and `gap-shop-match`/`garment-search`/`packing-brief` use a clean `{error: code, message}` via a local `fail()` helper; `quota.ts`, `transcribe-intake`, `stylist-chat` put a genuine machine-readable slug directly in `error`; `support-mail`, `superwall-webhook`, `superwall-reconcile`, `delete-account` put a free-text sentence in the same field; `generate-outfits` uses three different shapes across its own status codes in one function (`{error}` for 400/401/500, `{error,requiredVersion}` for 403, and a **200 OK** `{ok:false,reason,error}` for provider failure — `generate-outfits/index.ts:246-250`) — and its client's shared `classifyDenial()` helper (`src/features/billing/use-gate.ts:53-79`) only decodes 402/429, so a 403/500 thrown as an HTTP error falls through to a generic "offline" state indistinguishable from a real network outage (`src/app/(tabs)/index.tsx:1503`). Client-side consumption quality tracks the server shape directly: `stylist-chat`, `pinterest-api`, `parse-closet`, and `garment-search`'s search/match paths are genuinely code-aware (dedicated switch helpers on exact server codes); `support-mail`, `tag-item`, and `superwall-reconcile`'s clients likewise read structured responses correctly; `gap-shop-match` and `garment-search`'s partner-feed path deliberately discard errors entirely by spec; `delete-account` and `generate-outfits` leave real server-side structure unread (see #3, #5 above).

6. **`sync-feeds` is strictly sequential across merchants with a mandatory 13s inter-merchant gap and a 120s per-feed timeout, with no continuation/resume across cron ticks.** `supabase/functions/sync-feeds/index.ts:386-422` loops merchants one at a time (`FEED_GAP_MS=13_000` at line 62, `FEED_TIMEOUT_MS=120_000` at line 74) — a documented, deliberate Awin rate-limit constraint (lines 60-61: "forbids concurrent requests to the same feed"), not a bug. But as the joined-merchant count grows, total run time (`N × (feed time + 13s)`) has no ceiling and no checkpointing, so a run exceeding Supabase's Edge Function wall-clock limit would silently drop the remaining merchants until the next day's cron tick, with only the per-merchant `sync_error` column (line 418) as a signal.

7. **Inconsistent retry policy across the AI-calling functions**, all built on the same `_shared/openrouter.ts:completeStructured`: `analyze-inspiration`, `generate-outfits`, `packing-brief`, `tag-item`, and `stylist-chat` all retry once with 600ms×(attempt+1) backoff on retryable (429/5xx) errors; `garment-search`'s `search`/`match` calls and `parse-closet`'s fallback call make a **single attempt with no retry** (`garment-search/index.ts` ~line 866 comment: "one provider call, no retry loop"; `parse-closet/index.ts:318-321`). `parse-closet` is notable because its own file header documents a near-miss production timeout that motivated a model swap (`parse-closet/index.ts:58-73`) — the function with the most-documented history of timeout close calls is also the one with zero retry protection against a transient provider hiccup.

8. **`commerce-health` compares its cron/ops shared secret with a plain `!==`** (`supabase/functions/commerce-health/index.ts:64`) rather than the constant-time comparison used for the equivalent secret in `build-export` (`constantTimeEqual`, `build-export/index.ts:72-77`), `superwall-webhook` (`:51-56`), `sync-feeds`, and `reap-intake-audio`. Low real-world risk (an operator/cron secret gating a reporting endpoint, not a financial mutation, over HTTPS) but an internal-consistency gap worth aligning.

9. **`pinterest-oauth`'s `/callback` does not independently validate `redirect_uri` against a local allowlist** — it's derived from the incoming request's own origin (`callbackUri()`, `pinterest-oauth/index.ts:45-50`) and passed straight to `exchangeCode`, relying on Pinterest's own app-console URI matching (standard OAuth2 behavior) rather than a local check. The state-token CSRF protection itself is exemplary (32 random bytes, 10-minute TTL, single-use via one atomic `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now()`, proven in `supabase/tests/26_pinterest_connection.sql`) — this is a narrower note about defense-in-depth on the redirect URI specifically, not a finding against the CSRF design.

10. **`stylist-chat` interpolates the user's raw chat message into the LLM prompt with no escaping**, bounded only by length: `parts.push(\`THEY ASKED\n${message}\`)` (`stylist-chat/index.ts:260`), message capped at 2000 chars (`_shared/input-bounds.ts` `CHAT_LIMITS`). Blast radius is bounded by the response schema's `strict:true`/`additionalProperties:false` constraint and a closed vocabulary of known outfit ids (`_shared/chat-schema.ts:22-44`) — a successful injection can't fabricate structured fields — but the `reply` field itself is free text, so a crafted message could still attempt to steer the model's tone/content within the system prompt's guidance. Real but bounded-impact surface; the same pattern (raw interpolation, schema-constrained blast radius) recurs in `generate-outfits` and `packing-brief`.

11. **`send-push` is deployed, cron-scheduled, and has the best timeout/retry coverage in the codebase (20s `AbortSignal.timeout`, one retry with 800ms backoff on 408/429/500/502/503/504, `_shared/push.ts:203-249,335-384`) but has never delivered a real notification in production** per its own docblock (`send-push/index.ts:56-64`): `push_tokens` is empty pending a store build with `expo-notifications`/`aps-environment` configured. Not dead code (it's correctly wired, atomically claimed, and scheduled — `supabase/migrations/20260810110200_push_cron.sql:141-156`), but worth flagging as "shipped and unverified in production" rather than "shipped and proven."

12. **`superwall-webhook` and `superwall-reconcile` both correctly use atomic, idempotent RPCs for duplicate-delivery handling** (`claim_superwall_event` at `superwall-webhook/index.ts:223-226`, `claim_superwall_alias` at `superwall-reconcile/index.ts:77-80`) — flagged as a **positive** finding since idempotency was an explicit audit ask: Svix at-least-once delivery is handled via `svix-id` claim-before-decide (`:188-203`), constant-time HMAC comparison (`:51-56`), and a 5-minute replay tolerance (`:49,78-82`). By contrast, `asc-notifications` achieves idempotency by a different mechanism — `notification_uuid` is upserted as a primary key (`asc-notifications/index.ts:336-351`) but there is no pre-check short-circuiting the mutation path before a redelivery re-runs it; correctness instead relies on `isStale()`'s data comparison (`_shared/superwall-plan.ts:96-102`) making re-application a no-op. Functionally sound in both cases, but a genuinely different (less explicit) idempotency shape worth normalizing if `asc-notifications` is ever revised.

13. **Every cron/webhook-only function fails closed on a missing shared secret**, confirmed directly across `sync-feeds` (`index.ts:338-345`), `reap-intake-audio` (`:50-53`), `send-push` (`:161-164`), `commerce-health` (`:59-63`), `build-export`'s sweep path (`:151-154`), and `superwall-webhook` (`:135-141`) — none default to accepting requests when their gating secret is unset. Called out as a positive finding since fail-open-on-missing-secret is one of the more common ways cron-only functions get accidentally exposed.

14. **Pinterest's documented "missing `CLIENT_SECRET` is the pending signal" behavior is confirmed fail-closed, not crash-prone**, in both functions that touch it: `pinterest-oauth`'s `/start` returns `{error:'not_configured'}` 503 (`index.ts:157-162`), and `pinterest-api` falls through its generic catch to `{error:'provider_down'}` 503 (`index.ts:129-142`) — neither throws an unhandled exception or 500s with a stack trace, and neither ever echoes the secret's name or value.

15. **`_shared/catalog.ts` has restrictive filesystem permissions (`-rw-------`, owner-only)** while every other file in `_shared/` is `-rw-r--r--`. Not a security control (source under git; permissions don't travel with the repo), likely an accidental local `chmod` — worth normalizing since it's inconsistent with the directory and could mask a review-tooling gap if CI ever checks file modes.

### Group A — analyze-inspiration, asc-notifications, build-export, commerce-health, delete-account

- **Error shape**: `{error: string}` throughout, no `code` field (index.ts:57-59,68,78,88,101-104,128,131,140,213-215); 403/429 bodies use `error` itself as a slug. **Client gap**: `src/features/recreate/use-recreate.ts:58-70` handles 403/429/503 but not 402 (`plan_upgrade_required`) — falls through to generic `'unreadable'`. Not reachable today since `inspiration` has a nonzero limit on every plan, but the client-side gap exists.
- **Timeouts/retries**: `AbortSignal.any` covering header+body read, 45s (index.ts:49); 2-attempt retry with 600/1200ms backoff on retryable errors only (index.ts:163-194).
- **Secrets**: `OPENROUTER_API_KEY` read in-handler (index.ts:55), not top-level; `redactUrls` strips signed-URL text before logging/ledger.

- **Perf**: 3 independent reads (`ai_consent_version`, `current_ai_consent_version` RPC, `taggingRow`) done as sequential awaits (index.ts:92-96,98,111-115) instead of `Promise.all`.

#### asc-notifications (`supabase/functions/asc-notifications/index.ts`, 367 lines)

Full Apple JWS chain verification: x5c pinned to `APPLE_ROOT_CA_G3_B64` (index.ts:96-98, asc-plan.ts:85-86), per-link issuer/signature/validity checks (index.ts:116-129), leaf signature via `jose.compactVerify` (index.ts:133-143), nested `signedTransactionInfo` independently re-verified (index.ts:221-228), bundle id checked (index.ts:230-235). `user_id` resolved only from the verified `appAccountToken` inside the payload (index.ts:271, UUID-shape checked) — no spoofing surface. #### delete-account (`supabase/functions/delete-account/index.ts`, 268 lines)
- **Auth**: `withSupabase({auth:'user'})`, `userId` from JWT only (index.ts:121-135); no request body parsed at all — zero spoofing surface.
- **Error shape**: `{error: <sentence>, detail?: 'mark_failed'|'delete_failed'}`, inconsistent with `build-export`'s `{error,code}` pattern and no stable `code` across all paths. **Client gap confirmed**: `src/features/auth/use-delete-account.ts:22-23` reads only the raw `error` message string, never the `detail`/`failedBucket`/`objectsRemoved`/`resumable` fields the server computes (index.ts:219-232,244-255); `src/app/privacy/delete.tsx:53-55` just interpolates `error.message` and always offers the same generic retry regardless of failure mode. - **Perf**: `listAllPaths` (index.ts:84-119) issues one `list()` call per item-subfolder — proportional to closet size — because Supabase Storage's `list()` has no recursive mode; not a code defect, a Storage API limitation. Object removal chunked at 100 (index.ts:74,197-203). The three buckets (`garments`, `avatars`, `intake-audio`) are processed sequentially (index.ts:194) rather than via `Promise.all`, trading a little latency for simpler partial-failure reporting — reasonable tradeoff.
- **Dead-function check**: live — `src/features/auth/use-delete-account.ts:18`, `src/app/settings.tsx`, `src/app/privacy/delete.tsx`. Not dead (App Store Guideline 5.1.1(v) mandatory deletion flow).

**Group A cross-cutting**: no hardcoded secrets found anywhere in these five directories or their shared imports; every `Deno.env.get()` call is inside a request handler, none at module top level — no cold-start-crash risk. Atomic quota/dedup patterns used correctly everywhere claimed. - **Perf**: the per-claimed-event outcome-ledger write loop (index.ts:172-179, `admin.rpc('note_superwall_outcome', ...)` per row) is sequential with no `Promise.all` — see Top-15 note; low impact given the loop is bounded by one user's own queued events.
- **Dead-function check**: live — `src/features/billing/use-alias-reconcile.ts:62` (`supabase.functions.invoke('superwall-reconcile', ...)`), which correctly types the full `ReconcileOutcome` response union. No cron/webhook (user-triggered on session establishment).

#### superwall-webhook (`supabase/functions/superwall-webhook/index.ts`, 363 lines)
- **Auth**: no Supabase JWT — `verify_jwt=false` (`supabase/config.toml:417-418`), documented rationale directly in both the migration comment and the function's own header (index.ts:6-31): Superwall has no Supabase session, so authentication is the Svix signature instead. Uses the **service-role key directly** rather than `withSupabase`.
- **Signature verification**: Svix HMAC-SHA256 over `id.timestamp.body` using the raw (unparsed) body bytes (index.ts:58-109) — correctly avoids the "parse then re-stringify" trap that silently breaks signature verification in frameworks that pre-parse JSON. Constant-time comparison (`constantTimeEqual`, index.ts:51-56). 5-minute replay tolerance against `svix-timestamp` (index.ts:49,78-82). Multiple `v1,<sig>` candidates checked (secret-rotation window support, index.ts:100-106) — any one matching passes.
- **Idempotency (explicit audit ask)**: genuinely well-built. `svix-id` is claimed via `claim_superwall_event` RPC **before** any business decision is made (index.ts:223-233) — "claimed" means finished-with, not merely seen, and the two paths that deliberately want a retry (`unmapped_product`, a failed subscription write) leave the id re-claimable rather than marking it done, so Svix's redelivery is preserved exactly where it's needed (index.ts:195-203 comment, corroborated by the `unmapped`/`write_failed` branches at index.ts:280-286,342-351). A `firstDelivery !== true` short-circuits to `{ok:true, applied:false, reason:'duplicate'}` (index.ts:235-239) without re-running any side effect.
- **Out-of-order delivery**: explicitly handled — `expirationAt` is the authority on recency, and an event describing a period no later than what's already stored is dropped as stale (index.ts:291-317) rather than applied in arrival order, which the code correctly notes could otherwise downgrade a user who just renewed.
- **Write correctness**: uses `.upsert(...).select('user_id')` rather than `.update()` specifically because a PostgREST `.update()` against a missing row returns 200/no-error/zero-rows — the comment (index.ts:319-328) identifies this as the exact failure mode that would silently drop a purchase for a user whose `subscriptions` row never got created, and the `.select()` is there so the write "proves itself."
- **Secrets**: `SUPERWALL_WEBHOOK_SECRET`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` all read inside the handler (index.ts:135,182-186), not top-level. Missing secret fails closed with a 500 and an explicit "refusing every delivery" log line (index.ts:136-141) rather than degrading to accept-all.
- **Error shape**: `{error: <sentence>}`, no `code` field — see Top-15 #5.
- **Dead-function check**: no client caller (expected, pure inbound webhook); no cron; registered externally in the Superwall dashboard, confirmed by the function's own docblock and `verify_jwt=false` override rationale in `config.toml:406-418`. Not dead.

#### support-mail (`supabase/functions/support-mail/index.ts` 438 lines + `mail.ts` 265 lines)
- **Auth**: `withSupabase({auth:'user'})` (index.ts:299-300); `userId` only from `ctx.userClaims?.id` (index.ts:306), 401 if absent. The sender's `email`/`handle` used in the outbound mail are read from the JWT's own account (`auth.admin.getUserById`, index.ts:381-382) and `profiles.username` (index.ts:380) — never accepted from the request body, so a caller cannot spoof the reply-to address or claim to be someone else (index.ts:393-397 comment makes this explicit).
- **Input validation**: the most thoroughly bounded input handling found in this audit. Byte-based body cap (2MB, distinct from the shared 64KB AI-prompt cap, with the difference explicitly justified — index.ts:138-152) via a hand-rolled `readBoundedBody` (index.ts:153-179) rather than the shared helper (deliberately, since this isn't an AI-prompt endpoint); per-field char caps (`topic`≤64, `body`≤4000, `query`≤200, `articleId`≤120, up to 24 diagnostic keys ≤40 chars/≤200 chars each — index.ts:74-92); attachment MIME allow-list (`image/{jpeg,png,webp,gif,heic,heif}`, `application/pdf`, index.ts:102-110) plus base64-charset validation and an explicit `data:` prefix rejection with an actionable message (index.ts:274-282); attachment filename reduced to a leaf name with control characters stripped before it can reach a mail header or a filesystem (index.ts:284-289).
- **Error shape**: `{error: <sentence>}` via a local `fail()` helper (index.ts:134-136), with one documented exception: the platform's own 401 (from `withSupabase`/`verify_jwt`) answers `{code, message}` instead (index.ts:66-70) — this is the one place in the entire codebase where that shape is used, and it's explicitly called out in the file's own docblock as differing from every other status this function returns.
- **Client caller confirmed thoroughly code-aware**: `src/features/help/support-mail.ts:150-175` distinguishes 429 (throttle, reads and displays the server's own sentence since only the server knows the cooldown), 404 (reads as "not deployed yet," not "rejected" — a deliberate distinction for the mid-rollout window), and falls back to `sentence ?? - **Timeouts/retries**: `postResendEmail` (mail.ts:112-146) uses a 15s `AbortController` timeout, no retry (single attempt, acceptable for a synchronous user-triggered send with an explicit "not sent" response rather than a false success).

- **Secrets**: `RESEND_API_KEY` read inside `postResendEmail` (mail.ts:113), not top-level; missing key returns `{sent:false, reason:'not_configured'}` rather than crashing, and the 503 response is explicit that this is a known, expected state today (mail.ts:21-24). Errors from Resend are logged as status-only, never the request body — explicit comment that "the request is somebody's private message" (mail.ts:130-133).
- **Perf**: `profiles.username` select and `auth.admin.getUserById` are correctly run via `Promise.all` (index.ts:379-383) — a positive counter-example to the sequential-independent-reads pattern flagged elsewhere in this audit.
- **Dead-function check**: live — `src/features/help/support-mail.ts:140`, `src/app/help/write.tsx`. No cron/webhook.

#### tag-item (`supabase/functions/tag-item/index.ts`, 443 lines)
- **Auth**: `withSupabase({auth:'user'})` (index.ts:59-60); `userId` only from `ctx.userClaims?.id` (index.ts:94), 401 if absent. `itemId` from body is only ever read through the RLS-scoped `db` client (index.ts:121-125), so another user's item reads as 404 (index.ts:127-129) rather than leaking existence.
- **AI-consent gate**: checked server-side against `profiles.ai_consent_version` and a live `current_ai_consent_version()` RPC (index.ts:102-117) — explicitly justified as server-side because "a client-side gate is trivially bypassed" (index.ts:99-101), directly relevant to App Store Guideline 5.1.2(i).
- **Idempotency/exclusive claim**: `claimItemJob`/`completeItemJob`/`releaseItemJob` (`_shared/job-claim.ts`, called index.ts:159,394,438) provide an exclusive per-item claim so the upload queue's concurrency-3 retries can't double-charge the vision model for the same photograph — every early-return path (disabled workload, unreadable image, quota exhausted, write failure) explicitly releases the claim so a retry isn't permanently blocked (index.ts:214,225,241,394,432).
- **Quota ordering**: `enforceAiQuota` is claimed **last** — after the kill-switch check and after the image is proven readable via a signed URL — specifically because `claim_ai_quota` never refunds, and the file's own comment (index.ts:229-236) quantifies the alternative: with the client's queue retrying at concurrency 3, claiming quota before a config/image check would let a disabled workload or broken image "drain a free user's month in seconds instead of stopping spend." This is the clearest documented instance in the codebase of the general principle stated in `_shared/quota.ts`'s own header.
- **Retry/rescue model logic**: two-attempt loop distinguishes a *retryable provider error* (429/5xx, re-runs the same model) from a *deterministic validator rejection* (escalates once to a configured rescue model, never loops further) — these are different failure classes handled differently on purpose (index.ts:272-366), and both paths are correctly reflected in the `ai_calls` ledger via `attemptsMade`, which the code notes would otherwise "make the tagger's true provider volume unknowable" if hardcoded to 1 (index.ts:260-269).
- **Error shape**: `{error: <sentence or slug>, detail?}` — inconsistent field usage across paths (compare index.ts:65-68's slug-like `error: 'OPENROUTER_API_KEY is not configured.'` sentence vs. index.ts:184's `error: 'This item is already being tagged.'` sentence vs. the 200-with-`ok:false` shape at index.ts:396-399 for a graceful tagging failure).
- **Perf**: the `profiles.ai_consent_version` select and `current_ai_consent_version()` RPC (index.ts:102-110) are independent sequential awaits that could be `Promise.all`'d — the same pattern flagged in `analyze-inspiration`, `generate-outfits`, `packing-brief`, and `stylist-chat`; this makes it a five-function repeat of one micro-optimization, worth fixing once in a shared helper rather than five times individually.
- **Dead-function check**: live — confirmed via `src/features/ingest/upload-queue.ts` (multiple call sites) and `src/features/closet/item-write.ts`. No cron/webhook.

#### transcribe-intake (`supabase/functions/transcribe-intake/index.ts` 245 lines + `asr.ts` 243 lines)
- **Auth**: `withSupabase({auth:'user'})` (index.ts:52-53); `userId` only from `ctx.userClaims?.id` (index.ts:65), 401 if absent. Two purposes share one auth path — bulk `walkthrough` (session-scoped, reads/writes `intake_sessions` via the RLS-scoped `db` client, index.ts:129-133) and single-utterance `catalogue-query` (index.ts:213-245, takes no `db` parameter at all — the isolation from `intake_sessions` is enforced by the function signature, not by convention, and is asserted by `tests/transcribe-contract.test.ts` per the file's own comment, index.ts:201-206).
- **Path safety**: the stored-audio object path is built server-side as `${userId}/${objectName}` (`asr.ts:97`) — the caller only ever supplies the filename half (itself constrained to a UUID-shaped `requestId` for `catalogue-query`, validated by regex before use, index.ts:47,88-89), so there's no argument through which a request can name another user's object (asr.ts:80-84 comment makes this explicit).
- **Size/duration caps**: `MAX_BYTES=25MB` and `MAX_DURATION_MS=12min` (asr.ts:37-38) enforced server-side regardless of client-side enforcement — checked against the object's actual stored size via a `storage.list()` metadata read (asr.ts:108-115) before the provider call, and an oversized object is deleted immediately (asr.ts:112-114) rather than left around.
- **Deletion-as-the-feature**: audio is deleted the moment a transcript exists and before anything else can fail (index.ts:172-175,238), with the explicit design note that a transient failure leaves the object in place so a retry doesn't force the user to speak again, and `reap-intake-audio`'s 24-hour age-based sweep is the backstop either way (index.ts:32-38) — a genuinely well-thought-out data-minimization design, directly relevant given this handles raw voice recordings.
- **Timeouts/retries**: single attempt, no retry (asr.ts explicit design, not an oversight — `DEFAULT_TIMEOUT_MS=120_000` floor with the real bound coming from DB-configured `ai_config.timeout_ms` for `voice_transcription`, asr.ts:43-48,99-103); timeout applied via `AbortSignal.timeout()` on both the signed-URL audio fetch and the provider POST (asr.ts:160-162,189-194).

The fix (explicit `response_format:'json'`) is now centralized in the shared `asr.ts` core specifically so it can't regress in a second caller — a good example of a fix being structurally prevented from recurring rather than just patched once.
- **Quota**: `enforceAiQuota(..., 'tagging')` claimed before the provider call in both purposes (index.ts:145,223), never refunded — same posture as every other AI endpoint in the codebase.
- **Error shape**: `{error: <slug>}`, no separate `message` field (index.ts:58-60,68,79,92,97-99,135,136,162,165,169,183) — but the slugs here are genuinely stable and enumerable (`no_audio`, `too_large`, `audio_unreadable`, `silent`, `bad_request`, `unauthenticated`), making this one of the cleaner machine-readable `error` conventions in the audit despite lacking a separate `message`.
- **Dead-function check**: live — `src/features/intake/use-transcription.ts:353`, `src/features/catalogue/use-catalogue-voice.ts`. No cron/webhook.

**Group D cross-cutting**: no hardcoded secrets found in any of the six functions or the `_shared/` files they import (`superwall-plan.ts`, `job-claim.ts`, `quota.ts`, `joined-programmes.ts`). Every `Deno.env.get()` call across all six is inside a request handler, never top-level — no cold-start-crash risk from a missing var. Atomic RPC-based quota/dedup/idempotency patterns hold in every function that claims one: `claim_support_send` (support-mail, with a documented, quantified fix of a prior real race), `claim_superwall_alias`/`note_superwall_outcome` (superwall-reconcile), `claim_superwall_event` (superwall-webhook), `claim_ai_quota` (tag-item, transcribe-intake), `claimItemJob`/`completeItemJob` (tag-item). `support-mail`'s `Promise.all` for its two independent reads (index.ts:379-383) is the one function in this group that already does what the "sequential independent awaits" finding asks for elsewhere — worth pointing other functions at as the reference pattern.
